1. PROJECT OVERVIEW
================================================================================

Fitsy is a premium fashion e-commerce storefront with a Virtual Try-On (VTO)
feature. Users can browse products across categories (Clothes, Glasses, Shoes,
Jewelry, Makeup, Accessories), add to cart, save to wishlist, and preview items
using their webcam via an AR overlay.

The frontend is a React + Vite single-page application. As of the current build
it is fully self-contained — auth, cart, and wishlist are all powered by
localStorage with no backend calls. The refactor described in Section 9 makes
it integration-ready for the Express + MongoDB backend (see /backend).

4. ARCHITECTURE & DATA FLOW
================================================================================

  Provider tree (App.jsx):
    AppErrorBoundary
      AuthProvider           ← user session, JWT token
        ProductsProvider     ← product catalog (API or static)
          StoreProvider      ← cart + wishlist (uses AuthContext for user)
            Router
              Navbar
              <Routes>
              Footer

  Data flow:
    1. On app load, AuthProvider reads saved session from localStorage.
    2. StoreProvider listens to AuthContext for user changes and loads
       cart + wishlist (from API if backend enabled, else localStorage).
    3. ProductsProvider fetches product catalog from API on mount;
       falls back to static PRODUCTS array if fetch fails or no VITE_API_URL.
    4. Pages/components consume contexts via hooks:
         useAuth()     → user, isAuthenticated, loading, error, login, register, logout
         useStore()    → cartItems, wishlistItems, addToCart, removeFromCart, toggleWishlist
         useProducts() → products, categories, loading, error, getProductById

  Mode detection (IS_BACKEND_ENABLED):
    const IS_BACKEND_ENABLED = Boolean(import.meta.env.VITE_API_URL);
    - If VITE_API_URL is set → contexts call the API, token is managed
    - If not set → localStorage mock (fully functional for demo/dev without backend)

5. KEY FILES EXPLAINED
================================================================================

  src/data/products.js
    - Defines CATALOG_BLUEPRINTS (grouped by category with vtoType, sizes)
    - Generates PRODUCTS flat array by flattening blueprints into 54 items
    - Each product: { id, name, price, rating, accent, badge, image, category,
      vtoType, sizes, inventory, description, tryOn? }
    - tryOn is only on Glasses products: { overlayKey, widthMultiplier, bridgeOffsetY }
    - Acts as the static fallback even after backend integration

  src/components/AROverlay.jsx
    - Full AR pipeline: getUserMedia → MediaPipe FaceLandmarker → canvas-free
      face tracking via CSS absolute positioning
    - Two modes:
        face-tracking (Glasses): places SVG overlay on detected face landmarks
        guided-preview (all others): overlays product image on a static guide
    - Falls back gracefully if camera is denied or MediaPipe fails to load
    - Does NOT currently call the backend (no session saving / analytics)

  src/components/ProductImage.jsx
    - Handles broken image URLs (common with Unsplash) by generating a
      category-styled SVG fallback using data URIs
    - Each category has its own color palette for the fallback art

  src/utils/safeStorage.js
    - All localStorage reads/writes wrapped in try/catch to handle
      private browsing, storage quota errors, etc.
    - safeStorageClearAll(keys?) added for logout cleanup

6. STATE MANAGEMENT
================================================================================

  AuthContext
    Stored  : session user object in localStorage (fitsy-auth-user)
    Mock    : user registry stored in localStorage (fitsy-auth-users)
    API     : POST /api/auth/login → { token, user }
              POST /api/auth/register → { token, user }
              POST /api/auth/logout
    Exposes : { user, isAuthenticated, loading, error, login, register, logout }
    Note    : login() and register() are async in both mock and API modes.
              They always return { success: bool, message?: string, user?: obj }

  StoreContext
    Old API  (pre-refactor):
      getCartItems(userId), getWishlistItems(userId)
      addToCart({ userId, product, size })
      removeFromCart({ userId, productId, size })
      toggleWishlist({ userId, product })

    New API  (post-refactor):
      cartItems[]   — flat array, auto-scoped to logged-in user
      wishlistItems[] — flat array, auto-scoped to logged-in user
      addToCart({ product, size })         — async, optimistic update
      removeFromCart({ productId, size })  — async, optimistic update
      toggleWishlist({ product })          — async, optimistic update

    Cart item shape:
      { productId, size, quantity, name, price, image }
    Wishlist item shape:
      { productId, name, price, image, category }

  ProductsContext
    Source  : API GET /api/products → falls back to static PRODUCTS array
    Exposes : { products, categories, loading, error, getProductById(id) }
    Note    : getProductById checks both numeric id (static) and string _id (MongoDB)

7. VIRTUAL TRY-ON (AR) SYSTEM
================================================================================

  Trigger   : "Virtual Try-On" button on ProductPage → sets isAROpen = true
              → renders <AROverlay product={product} onClose={...} />

  Face tracking pipeline (Glasses category only):
    1. getUserMedia({ video: { facingMode: 'user', 1280×720 } })
    2. FaceLandmarker.createFromOptions (loads float16 model from Google CDN)
    3. requestAnimationFrame loop → detectForVideo() → face landmarks array
    4. Key landmarks used: 127 (leftTemple), 356 (rightTemple),
       33 (leftEye), 263 (rightEye), 168 (noseBridge), 10 (forehead), 152 (chin)
    5. Geometry: faceWidth, eyeDistance, faceHeight, centerX, centerY, rotation angle
    6. Validity checks: face size, geometry ratio, eyes-near-nose, inside stage bounds
    7. Smoothing: 72/28 EMA blend between previous and next style
    8. Output: CSS { left, top, width, transform } applied to overlay img element

  Overlay SVG map (GLASSES_OVERLAY_MAP):
    aviator, catEye, clear, oval, round, shield, square, wayfarer
    → Each product.tryOn.overlayKey maps to one of these SVGs

  Non-face products (Clothes, Shoes, etc.):
    → Product image shown as a static overlay with a body guide silhouette
    → CSS classes: ar-product--upper-body, ar-product--lower-body, etc.

  Fallback modes:
    'fallback' — camera denied or unsupported → static guided preview
    'loading'  — model/camera initializing → spinner
    'ready'    — camera + (optionally) face tracking live

8. BACKEND INTEGRATION GUIDE
================================================================================

  Step 1: Set environment variable
    Create frontend/.env.local:
      VITE_API_URL=http://localhost:5000/api

  Step 2: Start backend
    cd backend && node index.js   (or: npm run dev with nodemon)

  Step 3: Start frontend
    cd frontend && npm run dev

  The Vite dev proxy forwards /api/* → http://localhost:5000 automatically
  when VITE_API_URL is NOT set (empty BASE_URL in api.js → relative URLs).
  If VITE_API_URL is set, requests go directly to the full URL (no proxy needed).

  Step 4: Backend must implement these endpoints (see Section 11).

  Step 5: To build for production:
    cd frontend && npm run build
    → Outputs to frontend/dist/
    → Set VITE_API_URL to your production API base URL before building

11. API CONTRACT EXPECTED FROM BACKEND
================================================================================

  All routes prefixed with /api (or whatever VITE_API_URL is set to).
  All protected routes require: Authorization: Bearer <token>
  All responses: Content-Type: application/json

  ── Auth ──────────────────────────────────────────────────────────────────────
  POST /api/auth/register
    Body:    { name, email, password }
    Success: 201 { token: string, user: { _id, name, email } }
    Error:   400 { message: string }

  POST /api/auth/login
    Body:    { email, password }
    Success: 200 { token: string, user: { _id, name, email } }
    Error:   401 { message: string }

  POST /api/auth/logout         [optional — frontend clears token regardless]
    Success: 200 { message: 'Logged out' }

  GET  /api/auth/me             [optional — for restoring session on page reload]
    Success: 200 { user: { _id, name, email } }
    Error:   401

  ── Products ──────────────────────────────────────────────────────────────────
  GET /api/products
    Query params: category?, sort?, page?, limit?
    Success: 200 { products: Product[], total: number }

  GET /api/products/:id
    Success: 200 { product: Product }
    Error:   404 { message: string }

  Product shape expected by frontend:
    {
      _id:         string,       // MongoDB ObjectId as string
      name:        string,
      price:       number,
      rating:      number,
      category:    string,       // must match: Clothes|Glasses|Shoes|Jewelry|Makeup|Accessories
      vtoType:     string,       // upper-body|lower-body|shoes|jewelry|face|glasses|makeup|default
      sizes:       string[],
      inventory:   number,
      description: string,
      badge:       string,
      accent:      string,
      image:       string,       // URL
      tryOn?:      { overlayKey, widthMultiplier, bridgeOffsetY }  // Glasses only
    }

  ── Cart ──────────────────────────────────────────────────────────────────────
  GET  /api/cart                      → { items: CartItem[] }
  POST /api/cart
    Body:    { productId, size, quantity }
    Success: 200 { items: CartItem[] }
  PUT  /api/cart
    Body:    { productId, size, quantity }
    Success: 200 { items: CartItem[] }
  DELETE /api/cart/:productId/:size   → { items: CartItem[] }
  DELETE /api/cart                    → { items: [] }   (clear all)

  CartItem shape: { productId, size, quantity, name, price, image }

  ── Wishlist ──────────────────────────────────────────────────────────────────
  GET  /api/wishlist                  → { items: WishlistItem[] }
  POST /api/wishlist/toggle
    Body:    { productId }
    Success: 200 { items: WishlistItem[], added: boolean }

  WishlistItem shape: { productId, name, price, image, category }

12. OPEN QUESTIONS / FUTURE WORK
================================================================================

  Q1: VTO session tracking
    Should the AR try-on call the backend? E.g., log which products were
    previewed, save a snapshot, count try-on events. If yes, add:
    POST /api/vto/session { productId, timestamp }
    And call it from AROverlay.jsx when the camera becomes 'ready'.

  Q2: JWT persistence strategy
    Current: token stored in localStorage (survives page refresh, less secure).
    Production recommendation: httpOnly cookie set by the server (CSRF-safe).
    Mark: tokenStore.js has a comment pointing to this upgrade path.

  Q3: Products from backend or static?
    If the backend will expose GET /api/products from MongoDB, ProductsContext
    will use it automatically when VITE_API_URL is set.
    If products remain static, just don't set VITE_API_URL — the static fallback
    in ProductsContext handles it with zero code changes.

  Q4: Order history
    No order/checkout flow exists yet. When added:
    - New route: /checkout
    - New context or useAsync hook: OrderContext
    - Backend: POST /api/orders, GET /api/orders (paginated)

  Q5: Image hosting
    Product images currently use Unsplash URLs. For production, store in
    a CDN (Cloudinary, S3) and update MongoDB product documents with CDN URLs.
